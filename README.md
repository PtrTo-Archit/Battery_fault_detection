# AI-Based Lithium-Ion Battery Fault Detection

A software system that classifies Li-ion battery telemetry (voltage, current,
temperature) into normal operation or one of several fault types
(overcharge, over-discharge, overheat, short-circuit indication), built
with an explicit Software Quality Assurance process wrapped around the
ML pipeline.

Built for the Software Quality elective — see `docs/SRS.md` for the full
requirements specification and quality attribute definitions.

## Setup

```bash
git clone <your-repo-url>
cd battery-fault-detection
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Running the Pipeline (train a model)

```bash
python -m src.model
```

This automatically loads `data/battery_health_dataset.csv` if present
(the real NASA PCoE Li-ion discharge dataset, 24 batteries / ~29K
readings), engineers features per-cycle, labels faults, trains a
Random Forest, evaluates on a held-out set of *unseen batteries*, and
saves the trained model to `model.joblib`. If the real CSV isn't
found, it falls back to synthetic data so the pipeline still runs
end-to-end for development.

**Real results** (see `docs/SRS.md` Section 5.2 for the full
breakdown): 86.7% accuracy, 0.10% critical-fault false negative rate.

If you're using a different Kaggle/NASA battery CSV with different
column names, update `KAGGLE_COLUMN_MAP` in `src/model.py` to match.

## Running the API

```bash
uvicorn src.api:app --reload
```

Then visit `http://127.0.0.1:8000/docs` for the interactive OpenAPI
documentation (auto-generated by FastAPI — this doubles as living API
documentation for the quality report).

Example request to `/predict`:
```json
{
  "readings": [
    {"voltage": 3.7, "current": 2.0, "temperature": 25.0},
    {"voltage": 3.75, "current": 2.1, "temperature": 25.5},
    {"voltage": 3.8, "current": 2.0, "temperature": 26.0},
    {"voltage": 3.78, "current": 1.9, "temperature": 26.2},
    {"voltage": 3.9, "current": 2.0, "temperature": 27.0}
  ]
}
```
Note: at least 5 readings are required since rolling/delta features
need a short history — a single reading alone isn't enough (see
`docs/SRS.md`, FR-3).

## Quality Attributes (ISO/IEC 25010 mapping)

| Attribute | How it's addressed |
|---|---|
| Functional Suitability | Rule-based fault labeling documented and traceable to thresholds in `src/features.py` |
| Reliability | Input validation layer rejects malformed data before it reaches the model; critical-fault false negative rate reported separately from overall accuracy |
| Performance Efficiency | Random Forest chosen for fast inference without GPU requirements |
| Maintainability | Modular pipeline (validation → features → model → API), each independently unit tested |
| Usability | Auto-generated OpenAPI docs at `/docs`; clear HTTP error messages for invalid input |

See `docs/SRS.md` for the full specification.

## Quality Metrics Used

**Code & process metrics:** ≥80% test coverage (`pytest-cov`), cyclomatic
complexity graded via `radon`, static analysis via `pylint`, 41 automated
test cases, CI pass/fail history on every push, full requirements
traceability (`docs/traceability_matrix.md`), and a maintained defect log
(`docs/qa_process_and_defect_log.md`).

**Model / domain metrics** (real dataset results): 86.7% accuracy, 0.91
macro-precision, 0.87 macro-recall, 0.88 macro-F1, and a **0.10%
critical-fault false negative rate** — the last one is the key
domain-specific safety metric, tracked separately from accuracy since
missing a real overheat event matters far more than a false alarm does.

Full breakdown in `docs/SRS.md` Section 8.
